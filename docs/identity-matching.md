# Identity Matching: One Person, One Anchor

Author: Alex Scheaffer

The same person exists in HRIS, Active Directory, Entra ID, M365 and every SaaS app. Without a shared key, systems get matched by name or email, and those break on marriages, nicknames, duplicate names, rehires and typos.

**EmployeeID, issued by HRIS, is the only automatic join key.** Every other data point is used to *verify* a match, never to *make* one.

## Matching rules

| Situation | Result |
|---|---|
| Account's `employeeID` equals the HRIS EmployeeID | **Matched.** Automation manages the account |
| HRIS person has no account, and an account **without** EmployeeID has the same normalized first + last name | **Review:** "possible existing account." A human links the EmployeeID; automation never creates a duplicate |
| HRIS record has no EmployeeID | **Review:** fix in HRIS |
| Two HRIS records share an EmployeeID | **Review:** the account is left untouched until HRIS is fixed |
| Two accounts share an EmployeeID | **Review:** automation won't act for that person until resolved |
| Enabled account whose EmployeeID isn't in HRIS | **Review:** orphaned account; confirm the owner, then offboard or correct |
| Enabled account with no EmployeeID (and not a known service/admin pattern) | **Review:** link it, convert it to a service account, or disable it |

Name comparison is normalized (accents, apostrophes, spaces and case removed), so `José O'Brien` and `jose obrien` compare equal. It only ever raises a Review item.

## Who owns each attribute

| Attribute | System of record | Flows to |
|---|---|---|
| EmployeeID | HRIS | AD `employeeID` → Entra `employeeId` → SaaS (SCIM / SSO claim) |
| Name, preferred name | HRIS | AD → Entra |
| Department, job code, title, location | HRIS | AD attributes and role groups |
| Manager | HRIS (as manager's EmployeeID) | AD `manager` (resolved to the manager's account) |
| Employment status, start / end date | HRIS | Account enabled / disabled |
| Username, UPN, email address | Active Directory (generated by automation) | Entra, M365 → **HRIS via the email feed** |
| Role group membership | Lifecycle automation | AD → Entra |
| Resource group membership | Resource owners | AD |

Email is the one value that flows *back* to HRIS. Automation generates the address once, at account creation, and HRIS imports it by EmployeeID ([`ConvertTo-HrisEmailFeed`](../src/IdentityLifecycle/IdentityLifecycle.psm1)). Admin and service accounts are excluded so they can never become someone's email of record.

## Backfilling EmployeeID into an existing directory

An existing directory usually has accounts with no EmployeeID. The one-time backfill:

1. **Export** HRIS workers and AD users (UPN, mail, names, department, manager, created date).
2. **Pass 1, high confidence:** join on email / UPN where HRIS already stores it. Spot-check a sample.
3. **Pass 2, medium confidence:** normalized first + last name, confirmed by at least one more data point (department, manager or location). Every match is reviewed by a person.
4. **Write** `employeeID` to the confirmed accounts and let Entra Connect sync it.
5. **Everything left over** is an orphan, a service account or a shared account. Classify each one: link it, move it to `ServiceAccounts`, or disable it.
6. **Turn on automation in plan-only mode** and work the Review queue down to zero before applying anything.
